# EL Bot v0.7.0 Upgrade Plan

Status: LOCKED PLANNING SCOPE
Target: v0.7.0
Current released baseline under test: v0.6.0
Repository rule: main only; no feature/temp/staging branches.

## Purpose

v0.7.0 is the first post-v0.6.0 upgrade batch. It must combine the updater with all human-test defects discovered during v0.6.0 validation. The released v0.6.0 behavior stays frozen while evidence collection continues; fixes are implemented together as the v0.7.0 batch.

## Mandatory v0.7.0 scope

### 1. Full EL Bot updater

Build a user-facing updater that can:

- check the canonical EL Bot GitHub release source for a newer verified version;
- expose both automatic and manual `Check for Updates` behavior;
- compare semantic versions and never accidentally downgrade;
- show the available version and release notes/change summary;
- download the correct Windows installer/update payload with visible progress;
- retry/resume recoverably after network interruption;
- verify the downloaded payload against the release manifest and SHA-256 evidence before execution;
- preserve user settings/data across updates;
- safely hand off to the installer, restart EL Bot, and verify the new version after restart;
- report offline/unavailable/update-failed states truthfully;
- support the installed Setup flow and define safe behavior for Portable users;
- never report an update as installed until post-update verification succeeds.

### 2. ABC -> Emoji duplicate lexical/composition defect

Human-test reproduction:

- input: `credit card`
- expected canonical output: `💳`
- v0.6.0 observed winner: `💳 ➡️ 💳`
- alternatives showed the duplicated relation scoring about 321 with 100%/100%, while canonical `💳` scored about 193 with 50%/50%.

Required fix:

- investigate duplicate semantic/signature accounting across lexical resolution, phrase resolution, Phase-3 composition, candidate scoring, and round-trip validation;
- fix the root cause rather than special-casing `credit card`;
- add regression coverage for multi-word lexical concepts and duplicate/self-relation prevention.

### 3. Correct reverse translation incorrectly marked failed

Human-test reproduction:

- input: `🚲`
- output: `Bicycle.`
- visible semantic score: 100/100
- v0.6.0 UI simultaneously showed a red failure marker.

Required fix:

- make quality/status reporting consistent with the released winner and actual validation metrics;
- identify which hidden metric currently forces a failure state despite a correct winner;
- never show PASS-grade output and a contradictory failure badge without an explicit, user-understandable reason;
- add regression coverage for winner/status consistency in Emoji -> ABC mode.

### 4. Qwen/Ollama fallback, learning, and observability

Human-test evidence:

- input: `hopping`
- deterministic result: unresolved/unknown;
- `🦙🔍` probe returned `❌🦙📡` in the installed v0.6.0 app;
- runtime source is configured for local Ollama at `http://127.0.0.1:11434` and model `qwen2.5vl:7b`;
- Qwen is intended as a semantic teacher/fallback after a genuine deterministic FAIL, but the current user experience collapses provider-unavailable and genuinely-unresolved states into essentially the same visible failure.

Required fix:

- verify and harden the complete escalation chain: Forgey primary -> deterministic authority -> learned mapping -> Qwen/Ollama assist -> deterministic validation -> learning persistence;
- expose enough user-facing diagnostics to distinguish provider unavailable, provider error, assisted candidate rejected, learned candidate rejected, and genuinely unresolved input;
- never expose raw provider text directly as trusted EL output;
- only persist/reuse learned mappings that pass the deterministic validation/revalidation contract;
- add regression tests proving Qwen is called only at the intended FAIL boundary and that validated learning can be reused later without another provider call.

### 5. NEW: top-right Settings button (`⚙️`)

Add a persistent user-facing `⚙️` Settings button at the top-right of the EL Bot window.

The Settings surface must be the canonical place for user-available configuration. It should open a clear settings panel/modal without disrupting the current translation session.

#### Ollama / local AI settings

At minimum, provide:

- current Ollama connection status;
- base URL / endpoint, defaulting to `http://127.0.0.1:11434`;
- selected model, defaulting to the currently supported `qwen2.5vl:7b` unless the runtime contract changes;
- `Test Connection` / probe control;
- explicit states for Ollama unreachable, Ollama reachable but model missing, and ready;
- safe model discovery/selection from locally available compatible models where supported;
- validation before saving invalid endpoints/models;
- clear indication of whether Qwen fallback is currently available to translation.

#### Forgey settings/status

Expose only safe user-facing Forgey controls and evidence, including as appropriate:

- active Forgey generation/model identity;
- Forgey readiness/status;
- local model/runtime health and relevant diagnostics;
- user-adjustable Forgey options only when they are supported by the validation/safety contract;
- no hidden developer-only or unsafe bypass controls in the normal Settings UI.

#### Updater settings

The same Settings surface should include updater preferences such as:

- automatic update checks on/off;
- manual `Check for Updates`;
- current installed version;
- last successful update check/result;
- update channel only if more than one trusted channel is intentionally introduced later.

#### General settings contract

- settings must persist across app restarts and upgrades;
- changes must be validated before persistence;
- provide `Reset to Defaults` for user-available settings;
- preserve current translation/session state when opening/closing Settings;
- settings failures must be visible and non-destructive;
- no setting may silently weaken release verification, deterministic validation, or provider-safety boundaries.

## Acceptance gate for v0.7.0

v0.7.0 is not releasable until:

1. all locked v0.6.0 human-test defects have regression tests and verified root-cause fixes;
2. the updater passes install/update/restart/version-verification and network-failure recovery tests;
3. the `⚙️` Settings surface works and persists supported user settings;
4. Ollama/Qwen availability and fallback states are truthful and observable;
5. Forgey/deterministic/provider validation boundaries remain intact;
6. existing Phase-6 package/runtime/vision/44-engine regressions remain green;
7. human EASY, MEDIUM, HARD, IMAGE, OFFLINE, reboot, uninstall/reinstall, and update-path tests pass as applicable;
8. release publication again passes the transactional remote release verification contract.

## Change-control rule

Continue collecting v0.6.0 human-test evidence before implementing this batch. Do not hide or silently reinterpret failures. Investigate each defect before fixing it, then implement v0.7.0 as a coherent upgrade with updater + settings + validated defect fixes.
