# EL Bot v1.0.0 — Master Architecture & Product Separation Plan

Status: **LOCKED MASTER PLAN**
Target application release: **EL Bot v1.0.0**
Supersedes: `docs/V0.7.0_UPGRADE_PLAN.md`
Current released baseline: EL Bot v0.6.0
EL Bot repository: `doonchy16-cloud/EL_BOT`
Forgey-Insta:EL-Bot home repository: `doonchy16-cloud/forgey-insta-el-bot`
Repository rule for EL Bot: **main only; no feature/temp/staging branches.**

## 0. Executive architecture lock

EL Bot v1.0.0 is not a normal incremental update. It is a product-boundary correction.

The current v0.6.0 package embeds Forgey-Insta model/training artifacts and exposes a hidden Training Center in the same application. That architecture is now superseded.

The v1.0.0 architecture MUST establish two separate products with explicit responsibilities:

1. **EL Bot** = user-facing application, translation UI, deterministic authority/validation, model-release resolver, model downloader/cache, selected-model runtime adapter, settings, app updater, diagnostics, and safe fallback behavior.
2. **Forgey-Insta:EL-Bot** = the actual AI/model product. Its source, architecture, training data contracts, trainer, benchmarks, generation history, model artifacts, model manifests, model signatures, promotion gates, and model releases live in `doonchy16-cloud/forgey-insta-el-bot`.

EL Bot MUST NOT contain a trainable Forgey model as an application-owned generation, MUST NOT train or promote Forgey generations on ordinary user installations, and MUST NOT be hard-coded to `G2`, `G3`, a particular checkpoint path, or a particular Forgey release.

The only model product identity EL Bot may trust by default is the canonical Forgey-Insta:EL-Bot release source plus its signing identity/compatibility contract. The **specific model release** must be resolved dynamically.

## 1. Product ownership and trust boundaries

### 1.1 EL Bot owns

- the desktop application and installer;
- Emoji/ABC interaction UX;
- deterministic parsing, semantic accounting, validation, candidate scoring, quality reporting, and explicit unresolved-state handling;
- request lifecycle/cancellation/idempotence;
- native runtime adapter for a selected Forgey release;
- release discovery, compatibility filtering, download, verification, atomic installation, activation, rollback-to-last-known-good, and local caching of Forgey releases;
- user-facing Settings;
- app updater for EL Bot itself;
- safe diagnostics and observable model/runtime status;
- optional provider/Ollama configuration only where deliberately supported;
- no local model training.

### 1.2 Forgey-Insta:EL-Bot owns

- model architecture and model code;
- tokenizer and vocabulary artifacts;
- training curriculum and replay policy;
- teacher/provider evidence admission rules;
- trainer and evaluator;
- benchmark suites and protected probes;
- text + image capability training;
- generation registry for development/training;
- promotion policy between model generations;
- immutable model release artifacts;
- release manifests, hashes, signatures and compatibility metadata;
- developer/Owner training tooling;
- the canonical definition of `G1`, `G2`, ... for Forgey-Insta:EL-Bot.

### 1.3 No hidden coupling

EL Bot v1.0.0 MUST NOT depend on internal training-directory layouts in the Forgey repository. Integration occurs only through a documented release/runtime ABI and verified release artifacts.

The current EL Bot v0.6.0 embedded `G1/G2` material is classified as **legacy Phase-6 evidence/reference**, not the new canonical Forgey generation line. It may be used for comparison or migration research, but it MUST NOT silently become the new Forgey `G1`.

## 2. Real Forgey-Insta:EL-Bot G1 requirement

Before EL Bot v1.0.0 can ship, Forgey-Insta:EL-Bot MUST be built separately in its own repository and trained to a **real canonical G1**.

`G1` means the first independently released Forgey-Insta:EL-Bot model generation under the new repository and release contract. It must not merely rename the current embedded EL Bot `G2`.

The new G1 must have:

- an explicit architecture identifier;
- real trainable weights;
- deterministic tokenizer artifact;
- text inference capability;
- image/native-vision capability if declared in the release manifest;
- measurable training evidence;
- frozen evaluation benchmark not used as training truth;
- protected semantic probes;
- round-trip tests;
- adversarial/integrity tests;
- model-load tests;
- release-level SHA-256 hashes;
- a signed model manifest;
- reproducible generation metadata;
- proof that inference actually loads and executes the selected model weights;
- no claim of capability unsupported by measured evidence.

## 3. Proving EL Bot is using the actual AI

v1.0.0 MUST eliminate ambiguity about whether the displayed output came from the selected Forgey model.

Every Forgey inference result must carry internal evidence including at minimum:

- Forgey product ID;
- selected Forgey release tag/version;
- canonical generation ID;
- architecture/runtime ABI ID;
- model SHA-256;
- tokenizer SHA-256;
- model load state;
- inference attempted yes/no;
- inference released yes/no;
- inference latency;
- validator decision;
- fallback reason when Forgey does not release the answer.

Tests MUST prove real model use by at least:

1. selected-release hash assertion before load;
2. known model-only probe behavior tied to the released checkpoint;
3. negative test where the model artifact is unavailable/corrupted and Forgey inference cannot falsely report success;
4. release switch test showing the runtime loads the newly selected verified release rather than a hard-coded checkpoint;
5. runtime telemetry/diagnostics showing the exact release and hashes in use.

A deterministic fallback may still exist, but it must be labeled truthfully as fallback and never counted as Forgey inference.

## 4. Forgey release contract consumed by EL Bot

Each compatible Forgey GitHub Release must contain a signed manifest plus required artifacts. Proposed minimum manifest fields:

- `product_id: forgey-insta-el-bot`
- `release_version`
- `generation_id`
- `channel` (`stable` initially)
- `architecture_id`
- `runtime_abi_version`
- `minimum_el_bot_version`
- optional `maximum_el_bot_version`
- `model_asset_name`
- `model_sha256`
- `tokenizer_asset_name`
- `tokenizer_sha256`
- configuration/capability metadata
- text capability declaration
- vision capability declaration and image geometry if applicable
- context limit
- training-proof asset name/hash
- benchmark-proof asset name/hash
- release timestamp
- immutable release ID/tag
- signature/public-key identity metadata

EL Bot MUST reject a release if:

- manifest signature fails;
- required hashes fail;
- product ID is wrong;
- runtime ABI is incompatible;
- application-version compatibility fails;
- mandatory artifacts are missing;
- declared model metadata does not match loaded checkpoint metadata.

## 5. Model selection: dynamic, not hard-coded

EL Bot must never hard-code `G2`, `qwen2.5vl:7b`, or any Forgey checkpoint as the user’s Forgey model.

Forgey model selection policy:

- Default: **Latest Stable** — automatically resolve the newest compatible, signed Forgey-Insta:EL-Bot release published by Doonchy.
- Optional user choice: **Pin a specific compatible published Forgey release**.
- Users may switch only among trusted, compatible, published releases surfaced by the canonical resolver.
- Local arbitrary checkpoint browsing is not a normal-user feature.
- If a pinned release disappears remotely but is already verified locally, it may continue to run until the user changes selection, subject to revocation policy added later.
- If offline, use the last verified selected release.
- If no verified release is locally available, report Forgey unavailable explicitly; never pretend a bundled model is active.

This reconciles two product goals: users get the newest model by default, while advanced users can deliberately choose/pin a specific released Forgey model.

## 6. Forgey model installation/cache layout

Model releases MUST live outside the EL Bot installation directory, under persistent user data, for example:

`<EL Bot userData>/forgey/releases/<release-tag>/`

Each installed release folder contains only verified immutable assets plus a local verification receipt. Activation uses an atomic pointer such as `selected-release.json`.

Required transaction:

1. discover release;
2. download to staging directory;
3. verify manifest signature;
4. verify every asset hash;
5. verify compatibility;
6. load-probe candidate model;
7. write verification receipt;
8. atomically activate selection;
9. keep previous verified release as rollback candidate;
10. only then clean stale unpinned cache according to policy.

Failed downloads/verification must never alter the active model pointer.

## 7. End-user training is prohibited

Normal EL Bot users MUST NOT be able to:

- train Forgey;
- fine-tune Forgey;
- create a new generation;
- promote/reject generations;
- mutate model weights;
- add unverified training truth;
- alter protected benchmarks;
- bypass release signature/hash verification.

The v0.6.0 `Training Center` must therefore be removed from the distributed user training path. User Settings may show Forgey version/status/health and allow selection of a released model, but not training.

Any actual training UI/tool belongs to the Forgey-Insta:EL-Bot development environment/repository and is an Owner/developer function, not an end-user EL Bot feature.

## 8. Owner-only administration and universal Owner secret

Doonchy requires one extremely specific Owner secret known only to Doonchy, valid across installations, so distributed users cannot access Owner controls.

Security contract:

- the secret itself MUST NEVER be committed to either repository;
- MUST NEVER be stored plaintext in package resources, JavaScript, Python, release manifests, CI logs, issues, screenshots, or generated artifacts;
- MUST NOT be transmitted to a remote server for ordinary authentication;
- normal users do not create/change the Owner credential;
- no per-user bootstrap password flow in production builds;
- no user-accessible password rotation;
- Owner UI is hidden/privileged and is not the normal Settings UI.

Preferred implementation: ship only a cryptographic public verifier/public key derived from the Owner secret. On Owner unlock, derive/sign a local random challenge in memory from the entered secret and verify against the embedded public identity. A high-cost KDF must be used. Only verifier/public material may ship.

Important threat-model note: any universal client-side passphrase verifier can be attacked offline if an attacker extracts the binary. Therefore the Owner secret must have very high entropy. The build must not pretend a shared password is equivalent to hardware-backed authentication. A later optional hardware/security-key Owner identity may strengthen this further.

Owner access in distributed EL Bot should permit only explicitly required maintenance/diagnostic operations. **Training remains outside EL Bot even for Owner access** under this architecture.

## 9. Separate Forgey developer/Owner training environment

Training occurs in `doonchy16-cloud/forgey-insta-el-bot`, using a developer/Owner-controlled trainer or control room that is not shipped to ordinary EL Bot users.

That environment may provide:

- dataset ingestion and validation;
- teacher evidence collection;
- Qwen/Ollama teacher configuration;
- curriculum assembly;
- protected replay assembly;
- training start/pause/cancel/resume;
- live loss and resource metrics;
- candidate generation creation;
- benchmark evaluation;
- vision evaluation;
- promotion/rejection;
- release packaging/signing;
- release publication;
- rollback of the development production pointer.

## 10. Qwen/Ollama role after separation

Qwen/Ollama is not Forgey itself.

For v1.0.0 architecture:

- Forgey-Insta:EL-Bot is the primary model product.
- Qwen/Ollama may be used as a **teacher during Forgey development/training** under admission/validation rules.
- Optional runtime provider assist may remain only if deliberately supported, user-configurable, observable, and never confused with Forgey inference.
- EL Bot must not require Ollama in order to use a downloaded Forgey release.
- An Ollama outage must not make EL Bot claim the selected Forgey release is offline if Forgey itself is locally available.
- Provider-authored raw text must never become trusted EL truth without deterministic validation/admission.

## 11. User-facing Settings redesign

Top-right `⚙️` remains mandatory in v1.0.0.

Settings sections:

### Application
- installed EL Bot version;
- automatic app-update checks;
- manual `Check for EL Bot Updates`;
- last update result;
- persistent general preferences.

### Forgey-Insta:EL-Bot
- active release/tag;
- generation ID;
- model hash abbreviation;
- readiness/load status;
- `Latest Stable` vs pinned release policy;
- list of compatible signed releases;
- `Check for Forgey Updates`;
- download/verify/switch progress;
- last-known-good/rollback selection where safe;
- capability summary (text, image, context);
- no training controls.

### Optional Ollama/provider assist
- enabled/disabled;
- endpoint;
- selected compatible teacher/assist model if runtime assist is supported;
- connection test;
- explicit unreachable/model-missing/ready states;
- never presented as the active Forgey model.

## 12. Two independent updater systems

v1.0.0 needs two transactional update paths:

### 12.1 EL Bot app updater

Source: signed/canonical releases from `doonchy16-cloud/EL_BOT`.

Must verify release manifest + SHA-256, preserve user data/model cache/settings, hand off safely to installer, restart, and prove post-update version.

### 12.2 Forgey model updater/resolver

Source: signed/canonical releases from `doonchy16-cloud/forgey-insta-el-bot`.

Must resolve user policy (`Latest Stable` or pinned), compatibility-filter releases, download model assets transactionally, verify signature/hashes, load-probe, atomically activate, and preserve previous last-known-good release.

App and model versions are independent. Updating Forgey must not require rebuilding EL Bot as long as ABI compatibility remains valid.

## 13. v0.6.0 defect set carried into v1.0.0

All previously locked defects remain release blockers:

### A. `credit card` duplicate composition
Observed: `credit card` -> `💳 ➡️ 💳` instead of canonical `💳`.
Fix root cause in duplicate semantic/signature accounting; no literal special-case.

### B. reverse result/status contradiction
Observed: `🚲` -> `Bicycle.` but red failure while showing 100/100.
Quality status must reflect the actual validated result and expose any failing metric.

### C. subset output falsely scored 100/100
Observed mixed input `robot zxqvplmno credit card bicycle fox` collapsed essentially to `🚲` while visible metrics still showed 100/100.
Full source-concept accounting is mandatory. Missing required concepts must reduce score or force HOLD/FAIL.

### D. repeated Enter/request lifecycle
Repeated Enter/Run restarts or duplicates processing, including after completion.
Implement authoritative request IDs, in-flight idempotence, cancellation/supersession rules, stale-result rejection, and post-completion key-repeat protection.

### E. long-input semantic explosion
Long repetitive prose produces oversized repetitive EL chains.
Add semantic canonicalization/compression, density metrics, growth bounds, and tests that preserve meaningful repetition without mechanical duplication.

### F. image path incorrectly tied to Ollama availability
Native Forgey vision and optional provider assist must be distinct. A provider outage cannot mask a valid local Forgey vision path.

### G. provider/fallback observability
Distinguish Forgey release unavailable, Forgey rejected, deterministic fallback, learned mapping, provider unavailable, provider rejected, and genuinely unresolved input.

### H. `ChatGPT` imperfect round-trip regression case
Keep as a measured regression case rather than declaring success based only on plausible emoji composition.

## 14. Additional v1.0.0 quality requirements

- no fake data, fake status, fake training, or fake model selection;
- every visible model identity derives from verified runtime state;
- semantic quality cannot grade only a surviving subset;
- unresolved input must remain observable;
- candidate alternatives must never outrank a canonical phrase merely because duplicate bookkeeping inflated the score;
- long-running inference must remain cancellable and UI-responsive;
- UI should show which engine produced the released answer: Forgey / deterministic / optional provider-assist path;
- user data and selected Forgey release survive EL Bot upgrades;
- model download failures do not corrupt the previous model;
- a model release can be switched without reinstalling EL Bot when ABI-compatible.

## 15. Migration sequence

### Phase 0 — Freeze and classify
- keep v0.6.0 as historical released baseline;
- preserve current human-test evidence;
- classify embedded Phase-6 `G1/G2` as legacy reference, not new canonical generations;
- no new end-user training features in v0.6.0.

### Phase 1 — Bootstrap Forgey home repository
- establish architecture/docs/runtime/training/release directories;
- define model ABI and manifest schema;
- define signing/verification identity;
- import only reusable model/training components intentionally, preserving provenance;
- do not blindly copy EL Bot application coupling.

### Phase 2 — Build and train canonical Forgey G1
- establish deterministic datasets/training truth boundaries;
- train a genuine independent G1;
- run text, round-trip, protected, adversarial and vision gates;
- prove real checkpoint inference;
- package and sign G1 release;
- publish only after all G1 release gates pass.

### Phase 3 — Build EL Bot Forgey Release Resolver
- remove hard-coded generation/checkpoint assumptions;
- implement release discovery/compatibility filtering;
- implement transactional download/verification/cache/activation;
- load the selected release through stable ABI;
- prove release switching and last-known-good recovery.

### Phase 4 — Runtime correctness rewrite
- fix semantic composition, coverage scoring, request lifecycle, long-input compression, vision routing and fallback observability;
- make actual selected Forgey release the real model execution path.

### Phase 5 — Settings + updater
- top-right Settings;
- Forgey release selector/update controls;
- optional provider settings;
- EL Bot application updater;
- persistence across app/model upgrades.

### Phase 6 — Owner security conversion
- remove per-install Owner bootstrap/rotation from distributed builds;
- implement universal Doonchy-only Owner unlock using public-verifier design;
- ensure no secret is in source/build/logs;
- remove end-user training controls completely.

### Phase 7 — v1.0.0 system certification
- application installer/update tests;
- model fresh-install/download tests;
- latest-stable and pinned-release tests;
- model-switch tests;
- corrupted/missing release tests;
- offline last-known-good model test where possible;
- Easy/Medium/Hard/Image regression suite;
- 44-engine or successor full diagnostics;
- user-data persistence test;
- owner-access negative tests;
- release publication remote verification.

## 16. Release gates for EL Bot v1.0.0

EL Bot v1.0.0 MUST NOT release until all are true:

1. Forgey-Insta:EL-Bot canonical G1 exists as a separately published, signed, verified release.
2. EL Bot contains no hard-coded Forgey generation/checkpoint selection.
3. Fresh EL Bot installation can discover/download/verify/load a compatible Forgey release.
4. Default `Latest Stable` policy selects the newest compatible verified Forgey release.
5. Pinning a compatible Forgey release works and persists.
6. Switching releases proves the runtime actually loads the selected checkpoint.
7. No normal user can train/promote/mutate Forgey.
8. Owner secret is absent from source and package; only public verifier material ships.
9. All carried v0.6.0 defects have root-cause fixes + regressions.
10. app updater is transactional and verified.
11. Forgey model updater is transactional and verified.
12. native Forgey inference works without requiring Ollama when the selected Forgey release supports the request.
13. optional provider state is truthful and separate from Forgey state.
14. semantic coverage cannot falsely show 100/PASS for materially incomplete output.
15. image routing distinguishes Forgey vision from optional provider assist.
16. request lifecycle is safe under repeated Enter/Run/cancel/supersession.
17. long-input output growth meets defined semantic-density bounds.
18. release state is verified remotely after publication, not inferred from workflow green alone.

## 17. Non-goals / prohibited shortcuts

- Do not rename the current embedded G2 to new G1.
- Do not ship a fake `Train` button.
- Do not let ordinary users train or fine-tune.
- Do not embed the Owner passphrase.
- Do not hard-code a Forgey model version merely to make tests pass.
- Do not make Qwen/Ollama equal to Forgey.
- Do not couple EL Bot releases one-to-one with Forgey releases.
- Do not silently fall back while claiming Forgey produced the result.
- Do not accept unsigned/unhashed arbitrary model artifacts as normal production models.
- Do not fix semantic defects with phrase-specific hacks.

## 18. Architectural north star

**EL Bot is the vehicle. Forgey-Insta:EL-Bot is the engine.**

Doonchy trains, validates and releases the engine from its own home repository. EL Bot users install the vehicle, receive/select a trusted released engine, and use it. Users may choose which compatible Forgey release they run, but they do not train it. The engine can advance independently of the vehicle, and the vehicle must truthfully prove which engine release is active.
